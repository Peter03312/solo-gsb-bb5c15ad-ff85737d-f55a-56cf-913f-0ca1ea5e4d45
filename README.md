# 无线麦克风频率协调工具

面向现场音频工程师的无线麦克风频率协调 Web 应用。录入设备频率后自动分析互调冲突，并在指定约束下自动协调出无冲突、总偏移最小的频率方案，支持方案保存与回放。

## 功能

- **设备管理**：录入最多 8 个设备（名称、工作频率 MHz、保护间隔 MHz），可锁定频道、编辑、删除
- **互调冲突分析**：对任意两个不同频道枚举 `|f1−f2|`、`f1+f2`、`|2f1−f2|`（含两种有序组合），标出落入任一频道保护区（载频 ± 保护间隔，含边界）的互调积，并显示来源频道对与受影响频道
- **自动频率协调**：在指定频段、步进、最大偏移内调整未锁定频道（锁定频道保持不动），通过回溯搜索找出**总偏移最小**的无冲突方案；总偏移相同时按录入顺序选择更低频率；无解时保持原值并说明原因
- **现场占用频段避让**：协调前可临时填写多个现场扫描到的占用区间（MHz，仅作为本次协调参数提交，不改动设备数据）；候选频道新载频的保护区与任一占用区间相交（端点相接也算）即不可用，重叠区间自动合并，实际避让的区间会随结果展示并记入保存的方案
- **现场扫描采样导入**：在自动频率协调页可直接粘贴无表头的两列 CSV（频率 MHz、电平 dBm），填写采样间隔 MHz 与占用阈值 dBm。服务端整批校验：两列均须为有限数值、采样间隔为正、非空记录最多 1000 条，任一错误都指出具体行号。通过后同频点取最高电平、按频率排序，将电平达到（≥）阈值的频点扩展为中心 ± 半个采样间隔的闭区间，并自动合并相交或端点相接的区间。界面先预览生成的区间，确认后与手填占用区间合并送入现有协调流程（保存方案时记录合并后的区间）；支持一键清除本次导入，原始采样不入库
- **方案管理**：保存协调方案、查看详情、**应用前预览**（按设备 ID 列出当前频率与目标频率，并列出全部检查结果）、确认后一次性写回设备、删除
- **安全改频指引**：对已保存方案生成只读的逐台改频步骤。要求当前配置无互调冲突且避开方案所存占用区间、目标配置通过与应用前预览相同的全套检查，否则逐条列出原因。每步仅将一台未锁定设备由当前频率直接改到目标值（不用临时频率、每台至多一次），每个中间配置均按当前保护间隔检查全部互调冲突与占用区间闭区间相交；搜索全部可能顺序并取设备 ID 序列字典序最小者，无可行顺序时明确提示，频率完全相同则显示无需改频。成功时逐步显示设备名称、改前/改后 MHz 与该步完整频率表；生成指引不写回设备或方案
- **应用安全**：方案应用必须先预览再确认。仅「已求解」、分配与当前设备一一对应且无重复、目标频率为 0～10000 MHz 内有限正数、锁定设备未改频、用当前保护间隔复算无互调冲突、且各设备保护区与方案所存占用区间不相交（闭区间判定）的方案才能应用；任一检查失败都会列明原因并禁止应用。预览成功签发绑定方案内容与全部设备状态的一次性确认凭据；确认时在同一 SQLite 事务内核对凭据、重做检查并一次性更新，期间设备或方案发生变化（或凭据缺失/过期）一律返回 409 且不写入任何设备，界面提示重新预览
- **持久化**：SQLite 存储设备与方案，容器重启不丢失

## 快速开始（Docker，单条命令）

```bash
docker compose up --build
```

一条命令完成依赖安装、数据库初始化与服务启动。启动后访问：

- **Web 界面**：http://localhost:3000
- **API 地址**：http://localhost:3000/api（如 `GET http://localhost:3000/api/devices`），端口 `3000`（宿主机映射见 `docker-compose.yml` 的 `ports`）

> 数据库首次启动时自动初始化（`CREATE TABLE IF NOT EXISTS`），无需额外迁移步骤。
> SQLite 数据文件存放在命名卷 `app-data` 中；停止容器可用 `docker compose down`。

### 必要配置（环境变量，均有缺省值）

| 变量 | 缺省值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | 服务监听端口（容器内固定暴露 3000） |
| `DATA_DIR` | `/app/data`（镜像内） | SQLite 数据库目录，已挂载命名卷持久化 |
| `PREVIEW_TTL_MS` | `600000` | 应用前预览确认凭据的有效期（毫秒，默认 10 分钟） |

## 本地开发（不用 Docker）

```bash
npm install
```

## 使用说明

1. **录入设备**：在「设备列表」中填写名称、频率（如 `512.000`）、保护间隔（默认 `0.25` MHz），可勾选锁定。也可点击「载入示例」快速填充 8 通道示例数据。
2. **查看冲突**：冲突分析随设备变更自动刷新，表格列出互调类型、互调积频率、来源频道、受影响频道及偏差。
3. **自动协调**：设置频段上下限、步进（如 `0.025` MHz = 25 kHz）、最大偏移；如有现场扫描到的占用频段，点「+ 添加占用区间」逐行填写下限与上限（MHz，如 `511.700`–`513.000`，可添加多行；整行留空自动忽略），再点「开始协调」。成功后可将结果「应用到设备」或「保存方案」。
4. **现场扫描采样导入**（可选）：在占用频段避让区的「现场扫描采样导入」框中，直接粘贴频谱仪导出的**无表头两列 CSV**（每行 `频率MHz,电平dBm`，如 `512.000,-85.3`；逗号或制表符分隔，空行忽略，最多 1000 条非空记录），填写「采样间隔 MHz」（如 `0.025`）与「占用阈值 dBm」（如 `-80`），点「解析并预览区间」。服务端整批校验：两列均须为有限数值、采样间隔为正、非空记录最多 1000 条；有错误时逐条指出**行号**，修正后重新解析即可。校验通过后按下列规则生成占用区间并在页面预览：
   - 同频点（Hz 精度）取**最高电平**，并按频率升序排序；
   - 电平**达到（≥）阈值**的频点扩展为中心 ± 半个采样间隔的闭区间（如间隔 `0.025` MHz、频点 `512.000` → `[511.9875, 512.0125]`）；
   - 相交或端点相接的区间自动合并。

   预览确认前不影响任何协调参数；点「确认导入并与手填区间合并」后，导入区间与上方手填占用区间一起提交，服务端再次统一校验并合并（同一闭区间语义），随后进入现有协调流程。协调结果页展示的、以及保存方案时记录的，均为**合并后的占用区间**（方案 `params.occupiedBands`）。点「清除本次导入」可移除本次确认的导入区间（预览态随解析自动刷新；原始采样文本只存在于浏览器，不写入数据库）。保存方案后，历史方案的预览、应用与安全改频指引均按合并后的区间执行闭区间避让检查。
5. **占用频段说明**：占用区间只随本次协调请求提交，不会修改任何设备数据；区间要求为有限数值且下限不大于上限，重叠或端点相接的区间会自动合并。只要某频道新载频的保护区（新频 ± 保护间隔）与任一占用区间相交（端点相接也算），该候选即不可用；其余候选仍按原有互调规则与总偏移排序求解。结果页会列出**实际参与避让的（合并后）区间**。若因此无解，会明确说明占用频段限制，所有频道保持原频率。
6. **方案回放与应用**：在「已保存方案」中查看历史方案（含当时使用的占用区间参数）。点击「预览后应用」打开预览弹窗，系统按设备 ID 列出每个设备的**当前频率与目标频率**，并依次执行下列检查；全部通过后「确认应用到全部设备」才可用：
   1. 方案已标记为已求解（未求解方案禁止应用）；
   2. 分配与当前设备一一对应且无重复设备 ID（设备被删除或新增均不通过）；
   3. 每个目标频率都是 0～10000 MHz 内的有限正数；
   4. 锁定设备的目标频率必须与当前一致（锁定设备不得改频）；
   5. 用设备**当前保护间隔**对目标配置重新计算互调冲突（冲突数须为 0）；
   6. 每个目标频率的保护区与方案所存占用区间做闭区间相交检查（端点相接也算相交；旧方案缺失占用区间参数时按空数组处理）。

   任一检查失败都会在弹窗中逐条列明原因，且不签发确认凭据、无法应用。预览成功后得到一次性确认凭据（10 分钟有效）；确认在**同一个 SQLite 事务**中核对凭据、把上述检查重做一遍并一次性更新全部设备频率。若预览后设备或方案被改动、凭据缺失或过期，服务端返回 `409 Conflict` 且**不写入任何设备**，界面提示「重新预览」。
6. **安全改频指引**：在「已保存方案」中点击「安全改频指引」，系统以当前设备与所选方案生成只读的逐台改频步骤。前置条件：当前配置无互调冲突且各设备当前保护区避开方案所存占用区间（闭区间），目标配置通过第 6 步所述全部应用检查；不满足时弹窗逐条列出原因。满足时搜索全部逐台改频顺序：每步仅把一台未锁定设备由当前频率直接改到目标值（不使用临时频率、每台至多一次），每个中间配置都按当前保护间隔检查全部互调冲突与占用区间闭区间相交。存在多个可行顺序时给出设备 ID 序列字典序最小者；无可行顺序时明确提示；频率完全相同则显示「无需改频」。成功时逐步列出设备名称、改前/改后 MHz 及该步完成后的完整频率表。指引为只读预览，不会写回设备或方案。
7. **删除方案**：方案删除不影响设备数据。

## 协调算法

- 每个未锁定频道的候选频率为 `原频 ± k × 步进`（`k × 步进 ≤ 最大偏移`），且必须落在指定频段内
- 现场占用频段：候选载频 `f` 的保护区 `[f − guard, f + guard]` 与任一（已合并的）占用区间相交即剔除该候选，闭区间判定、端点相接也算相交
- 扫描采样导入：服务端整批校验两列有限数值、正采样间隔、最多 1000 条非空记录（错误附行号）；同频点（Hz 精度）取最高电平并按频率排序，电平 `≥ 阈值` 的频点扩展为 `[f − interval/2, f + interval/2]` 闭区间，再按与手填区间相同的口径合并相交/端点相接区间
- 搜索目标：所有频道总偏移 `Σ|新频 − 原频|` 最小；同分时按录入顺序逐频道比较，取更低频率
- 采用带回溯的分支限界搜索，随频道逐个确定增量检查互调积；设节点上限（200 万）防止极端参数下搜索爆炸，触顶时返回当前最优并明确标注
- 无解时所有频道保持原值，并返回可读的原因说明

## API 概览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/devices` | 设备列表 |
| POST | `/api/devices` | 新增设备（最多 8 个） |
| PUT | `/api/devices/:id` | 更新设备 |
| DELETE | `/api/devices/:id` | 删除设备 |
| GET | `/api/conflicts` | 当前配置的互调冲突列表 |
| POST | `/api/scan/import` | 现场扫描采样导入（只读、不落库）：body 为 `{ text, interval, threshold }`，`text` 是无表头两列 CSV（频率 MHz、电平 dBm，逗号/制表符分隔、空行忽略、非空记录最多 1000 条），`interval` 为采样间隔 MHz（必须为正数），`threshold` 为占用阈值 dBm（有限数值）。整批校验两列为有限数值、间隔为正、记录上限，错误逐条附行号（`errors: [{line, message}]`，全局错误 `line` 为 null）返回 `400`。成功返回生成并合并后的区间 `bands: [{lo, hi}]` 与 `sampleCount/pointCount/interval/threshold`（同频点取最高电平、按频率排序、电平 ≥ 阈值的点扩展为中心 ± 半个间隔的闭区间、相交/相接自动合并） |
| POST | `/api/coordinate` | 自动协调（body：`bandMin/bandMax/step/maxOffset`，单位 MHz；可选 `occupiedBands: [{lo, hi}, …]` 现场占用区间 MHz，可由手填区间与 `/api/scan/import` 预览确认的区间合并而来，服务端校验有限数值与 `lo ≤ hi` 并自动合并重叠/相接区间，响应 `params.occupiedBands` 即合并后结果，保存方案时原样记录） |
| GET / POST | `/api/plans` | 方案列表 / 保存方案（列表与详情中 `params.occupiedBands` 缺省按 `[]` 返回） |
| DELETE | `/api/plans/:id` | 删除方案 |
| POST | `/api/plans/:id/preview` | 应用前预览：返回绑定方案内容与全部设备状态的确认凭据 `token`、按设备 ID 的当前/目标频率、检查项与占用区间；检查失败返回 `422` 并逐条列明 `reasons` |
| POST | `/api/plans/:id/apply` | 凭 `{ token }` 确认应用：同一 SQLite 事务内核对凭据、重做检查并一次性更新；凭据缺失/过期、状态变化或检查失败返回 `409`（响应含 `repreview: true`），不写入任何设备 |
| POST | `/api/plans/:id/switch-guide` | 安全改频指引（只读，不写回设备或方案）：当前配置无互调冲突且避开方案所存占用区间、目标通过应用前全套检查时，返回逐台改频步骤（设备名称、改前/改后 MHz、该步完整频率表），顺序为全部可行顺序中设备 ID 序列字典序最小者；前置检查失败返回 `422` 并逐条列明 `reasons`；无可行顺序返回 `solvable: false`；频率完全相同返回 `noop: true`（无需改频） |
| POST | `/api/seed` | 空库时载入示例数据 |

## 技术栈

Node.js 20 · Express 4 · better-sqlite3（WAL 模式）· 原生 HTML/CSS/JS（无前端框架）

```
├── server.js            # Express 服务与 API 路由（含安全改频指引、扫描采样导入）
├── db.js                # SQLite 连接与建表
├── lib/intermod.js      # 互调计算、自动协调与改频顺序搜索核心（纯函数，可独立测试）
├── lib/scan.js          # 现场扫描采样解析、整批校验与占用区间生成（纯函数，可独立测试）
├── public/              # 前端页面（index.html / app.js / style.css）
├── test/                # 核心算法与预览/应用/改频指引/扫描导入接口测试（node:test）
├── Dockerfile
└── docker-compose.yml
```
